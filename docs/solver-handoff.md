# 到達可能性ソルバー: 第 2 段階（A-2）への引き継ぎ

A-1（キャラクター 1 人ずつの到達可能性）を終えた時点の状態と、A-2 でやることをまとめる。設計の根拠は [ADR-0015](decisions/ADR-0015-reachability-solver.md)、受け入れ条件は [roadmap.md](roadmap.md) の「A: 解析ツール」にある。本メモと ADR が食い違う場合は、ADR を先に直す。

A-2 が終わったら、このファイルは削除するか、A-3 への引き継ぎに書き換える。

## 1. いまの状態（A-1）

`solveRoom(runtime, start, options)` が、パーティの各メンバーを 1 人ずつ解いて `SolveReport` を返す。

- 足場ごとに `reached`（検証済みの `ReplayFile` つき）か `unreached`（見つからなかった）を返す。
- 足場のグラフ（どの足場からどの足場へ、どのマクロの種類で移れたか）を返す。
- 上限（節点数、`step` の総回数、1 マクロの tick 数）を超えたら `complete: false` を返す。
- まだ無いもの: 切替とパーティ全体の探索、戻れない領域、到達できない理由、操作感の Property テスト。

### ファイルの役割（`packages/solver/src/`）

| ファイル | 役割 | A-2 で触るか |
| --- | --- | --- |
| `types.ts` | オプションと報告の型 | `Scope`、`FootholdReport`、`ScopeReport` を広げる |
| `footholds.ts` | 足場の列挙（`listFootholds`）、足場の索引（`FootholdIndex`）、いま立っている足場（`standingOn`） | 索引は複数メンバーに対応済み。`standingOn` は操作中のキャラクターを渡す |
| `probe.ts` | 何も無い部屋で最長押しのジャンプを実測する（`measureRise`） | 上昇量の上限（`measureRiseBound`）を足す |
| `macros.ts` | マクロの定義、1 tick の実行（`tick`）、マクロの実行（`runMacro`）、マクロの一覧（`groundMacros`、`edgeMacros`）、押下時間（`jumpHolds`） | 切替のマクロを足す |
| `search.ts` | 着地状態の幅優先探索（`explore`）、経路の入力列（`pathHelds`） | キーと、節点ごとのマクロの一覧をパーティ対応にする |
| `witness.ts` | 入力列からリプレイを作る（`replayFromHelds`）、再生による検証（`verifyWitness`） | 変えない。新しい報告もここを通す |
| `solve.ts` | 入口。対象ごとに探索し、証拠を検証して報告を組み立てる | パーティの対象、戻れない領域、理由を足す |
| `test-support.ts` | テスト用の部屋とランタイム（`roomRuntime`、`emptyRows`、`fill`） | 切替の規則と、キャラクターごとの値を渡せるようにする |

### 変えてはいけないこと

- **健全性のゲート**: 「到達できる」「戻れる」と報告するものは、必ず `verifyWitness`（`runReplayHeadless` で最初から再生し、足場の上に接地していること、hash が探索時の状態と同じこと）を通す。通らなければ例外にする。報告を弱めて通すことはしない。
- **物理は `step` だけ**: `step` を呼ぶのは `macros.ts` の `tick` と `probe.ts` だけ。エンティティの配列に書き込まない。`physics-guard.test.ts` がソースを検査している。ファイルを増やして `step` を呼ぶ場合は、このガードの期待値を理由つきで更新する。
- **証拠は探索木の親をたどって作る**: 同一視した節点への辺は、着地した状態が代表と少し違う。証拠の経路に使うと再生が一致しなくなる（ゲートで例外になる）。
- **固有値を書かない**: キャラクター名、タグ名、速度、タイルサイズは `PackRuntime` から読む。テストの値は、テストファイルと `test-support.ts` に閉じる。
- **決定論**: 乱数と時計を使わない。走査順は固定（マクロの一覧の順、節点の id 順、足場の列挙順）。`Map` の反復順に依存する処理を足すときは、キーで並べ替える。

## 2. A-2 の作業

順番に進める。各項目の終わりで `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm depcruise` を通し、コミットして push する。

### 2.1 切替のマクロとパーティの探索

目的: 2 人を切り替えながら行ける範囲を求める。「片方だけが届く足場」に、切替を使えばパーティとして届くことを示す。

- 対象: `Scope` に `{ kind: 'party', members }` を足す。`solveRoom` は、1 人ずつの結果に続けて、メンバーが 2 人以上で `canSwitch` が真のときだけパーティの結果を返す（1 人構成や `mode: 'never'` では出さない。データから導く）。
- マクロ: `{ kind: 'switch' }`。切替の cooldown（`world.party.cooldownTicks`）が 0 になるまで何も押さずに待ち、切替を 1 tick 押す。切替が起きたかどうかは `world.party.activeIndex` の変化で見る。変わらなければ `skipped`。
  - `requireGrounded` が真の規則では、接地中にしか切り替わらない。マクロは接地状態から始まるので、そのまま使える。
  - `placement: 'spawn'` の規則では、切替で位置が入口の spawn に移る。`step` の結果をそのまま節点にすればよい（ソルバーは位置を計算しない）。
  - 切替で当たり判定の箱が変わる。箱が壁に重なる場合の挙動は core の実装どおりで、ソルバーは `step` の結果を使うだけにする。切替の直後に接地していなければ、着地まで待つ。
- 空中での切替: `requireGrounded` が偽なら、ジャンプ中に切り替えられる。まず接地中の切替だけを実装し、テストが通ってから「ジャンプの頂点で切替」を足す（ジャンプのマクロに `switchAtApex` の派生を足す）。足さない場合は、ADR の「完全性の範囲」に「空中での切替は試さない」と書く。
- キー: 「操作中のキャラクターの番号、足元の高さ、x の量子、vx の量子、cooldown が残っているか」。`search.ts` の `keyOf` を広げる。
- マクロの一覧: 操作感はキャラクターごとに違いうる。`explore` の冒頭で 1 回だけ作っている `baseMacros` と `holds` を、操作中のキャラクターごとに作って引くようにする（`measureRise` もキャラクターごと）。
- 足場: パーティでは「誰かが立てる足場」をすべて数える。`FootholdIndex` はメンバーごとの足場を持っているので、パーティの報告では「部屋のタイルの並び」に束ね直す（同じタイルを 2 人が別の足場として持つため）。束ね方は、行と列の範囲が重なるものを 1 つにする。
- 証拠: `replayFromHelds` に渡す `StartState.party` を、パーティのメンバー全員にする。`verifyWitness` に渡すキャラクターは、終端で操作中のキャラクターにする。

テスト（fixture）:

- 「片方だけが届く足場」: 水の列の向こうに、もう片方の箱でしか入れない低い通路を置く、など。1 人ずつではどちらも届かず、パーティでは届く配置を作る。現在の `WALKER` と `SWIMMER` は箱と操作感が同じなので、`test-support.ts` にキャラクターごとの箱や操作感を渡せるようにする（core の `CharacterDef` にキャラクターごとの操作感の上書きがあるかを、先に `packages/core/src/runtime/` で確認する）。
- `cooldownTicks` の間は切り替わらないこと、`mode: 'never'` と 1 人構成ではパーティの結果が出ないこと。
- 証拠のリプレイに切替の入力が含まれ、再生で足場に着くこと。

### 2.2 戻れない領域

目的: 「到達できるが、開始の足場へ戻れない」足場を報告する。

- 「戻れる」は、検証済みのリプレイがあるときだけ報告する（ADR の「戻れない領域」）。足場に最初に着いた節点の正確な状態から `explore` をやり直し、開始の足場に着く節点が見つかれば、「行きの入力 + 帰りの入力」を 1 本のリプレイにして `verifyWitness` に通す。
- 節点のグラフを逆向きにたどる方法は、候補の絞り込みにだけ使う。逆向きで「戻れそうにない」足場から先に調べる、などに使ってよい。
- 予算: 足場の数だけ探索をやり直すので、`step` の総回数が増える。A-1 の実測は ADR の「ソルバーの定数」にある。足場ごとに予算を分ける、開始の足場に着いた時点で打ち切る（目標つきの探索）、のどちらかを入れる。
- 何を「戻れない」と呼ぶかを、実装の前に ADR で決める。
  - 案 A: 足場に最初に着いた状態から戻れない。
  - 案 B: 足場の上のどの到達状態からも戻れない。
  - 案 A は速いが、「足場の端に着いたときだけ戻れない」を「戻れない」と報告する。案 B は正確だが遅い。推奨は、案 A を既定にし、報告に「最初に着いた状態からの判定」と明記すること。
- 証明（`provenNo`）: 開始の足場が、戻る側のどの足場からも「上面 + ジャンプの上昇量の上限」より高ければ、戻れない。上昇量の上限は 2.3 の `measureRiseBound` を使う。
- 報告: `FootholdReport` に `return?: { status: 'verified' | 'provenNo' | 'notFound'; witness? }` を足す。

テスト（fixture）:

- 落ちたら戻れない穴（A-1 の oneway の fixture「降りたら高さが足りず戻れない」を使える）。`provenNo` になること。
- 階段状で戻れる配置。`verified` になり、リプレイが開始の足場で終わること。
- 高さは足りるが、マクロでは戻る経路が見つからない配置。`notFound` になること。

### 2.3 到達できない理由

目的: `unreached` の足場に、証明つきの理由か推定の理由を付ける。

- `enclosed`（証明）: 体を点とみなし、開始位置から空きタイルを 4 方向にたどる。タグ付きタイルは、そのキャラクターの文脈で `solidAt` を引く。パーティでは誰かが通れれば空き。oneway は空きとして扱う（広く見積もる側に倒す）。
- `tooHigh`（証明）: `measureRiseBound` で、最良の条件でのジャンプの上昇量を測る。パーティでは、メンバーの操作感の最も有利な値（最大の `jumpVelocity`、最小の `gravity`、重力を弱める各倍率の最小）を組み合わせた仮の操作感で測る。この上限と `enclosed` の連結だけで作った足場のグラフでも届かなければ、証明つきにする。A-1 では実装していない。`probe.ts` の `measureRise` を元に書く。
- `needsTag`（推定）: 部屋のタイルクラスに現れるタグを 1 つずつ足した仮のキャラクターで解き直し、届けばそのタグを理由にする。解き直しの回数だけ予算を使う。
- `tooHigh`（推定）と `tooFar`: 到達できた足場の上面と、目的の足場の上面の差を、実測した上昇量と比べる。不足分を px で出す。
- `budget`: `complete: false` のとき。
- `unknown`: どれでもない。
- 報告: `FootholdReport` に `blocker?: { reason; proven: boolean; detail? }` を足す。証明と推定を必ず区別する。

テスト（fixture）: 壁で閉じた足場が `enclosed`、高すぎる足場が `tooHigh` と不足 px、タグの壁の向こうが `needsTag`、上限を小さくすると `budget`。

### 2.4 操作感の Property テスト

目的: 操作感を変えたときに、届く足場が操作感の値から導いた結果どおりに変わることを確かめる。

- `fast-check` は `solver` の devDependency に入れてある（core と同じ版）。
- 高さ: `jumpVelocity` と `gravity` をランダムに選ぶ（1/256 px の倍数にして、和が正確になるようにする）。A-1 の `riseInPx`（`solve.test.ts`）と同じ式で上昇量を出し、`floor` の高さの棚は届き、1px 高い棚は届かないことを確かめる。1 回の探索は 10 ms 程度（ADR の実測）。
- コヨーテ: `coyoteTicks` を増やしても、届く足場の集合が減らないこと（単調性）。A-1 のコヨーテの fixture（天井つきの通路）を使える。
- 上限に注意: テスト全体で 10 秒以内に収める。`numRuns` を絞る。

### 2.5 M3 への拡張設計の詳細化

目的: ADR-0015 の「M3 への拡張」を、A-3 で実装できる粒度にする。実装はしない。

- 鍵と扉のグラフの節点と辺の型の案。
- 単調に増える状態（`grants`、フラグ）の不動点の計算手順と、止まることの根拠。
- 単調でないもの（鍵の消費、一方通行の exit、敵、移動床）の扱いの案。
- 部屋をまたぐ証拠のリプレイのつなぎ方。
- `docs/pack-spec.md` の exits、アイテム、フラグの定義を読み、食い違いがあれば「要確認」に書く。

### 2.6 上限の見直し

- パーティの探索と、戻れない領域の探索を入れたあとで、ADR の実測の表を取り直す。
- 既定の `maxNodes`（20,000）と `maxSteps`（20,000,000）を、実測に合わせて見直す。

## 3. A-1 で分かったこと

- 探索の速さは、おおよそ毎秒 130 万 step。空中制御と可変ジャンプがある操作感では、1 節点あたりのマクロが約 9 倍になる（押下時間 4 通り × 左右の入力 9 通り）。部屋の広さより、操作感の自由度が効く。
- 開始位置が接地していれば、開始の足場の証拠は 0 tick のリプレイになる。
- 部屋の外は solid として扱われる。部屋の最上段のタイルの上には立てない（足場に数えない）。
- `createWorld` の直後は、接地の接触フラグが立っている。空中の状態を作るテストでは、実際にジャンプさせる。
- 踏み外しのマクロは、その節点からの「歩く」が足場を外れたときだけ試す。足場の端から 1 量子以内の節点でだけ起きるので、マクロの総数は増えにくい。
- コヨーテタイムでしか届かない配置は、横の距離ではなく天井で作ると壊れにくい（A-1 の fixture）。横の距離で作ると、踏み切り位置の位相で結果が変わる。
- 1px のタイルで部屋を作ると、高さを 1px 単位で指定できる（`tileSize: 1`）。A-1 の高さの fixture はこの方法を使っている。

## 4. 検証の方法

- **壊して戻す確認**: A-1 では、次の改変をそれぞれ入れて、テストが失敗することを確かめた（19 件）。A-2 で足す機能にも同じ確認をする。
  - ゲート: 足場の確認を外す、hash の確認を外す、`solveRoom` がゲートを呼ばない、押した瞬間を入れない。
  - 探索: キーから x を外す、キーから y を外す、節点数の上限を外す。
  - マクロ: コヨーテのジャンプを外す、遅延 0 だけにする、すり抜け降下を外す、最長の押下時間を外す、押下を 1 tick 短くする、歩くを外す、`step` の上限を外す、tick の上限を外す。
  - 足場: タグを無視する、接地の確認を外す。
  - 対象: 1 人に絞らない。実測の上昇の tick 数を短くする。
- **実行時間**: ソルバーのテスト全体は約 7 秒（61 件）。10 秒以内を保つ。
- **PR 本文に書くこと**: fixture ごとの節点数と `step` の回数、「状態を変えるのは `step` と `cloneWorld` だけ」であること、壊して戻す確認の結果。
