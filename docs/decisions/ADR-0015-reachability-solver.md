# ADR-0015: 到達可能性ソルバー

- Status: Accepted
- Date: 2026-11-15
- 論点: 解析ツール（A-1、A-2）

## 背景

探索型アクションでは、能力タグや 2 人の切替で行ける場所が変わる。手作業のテストプレイでは、抜け道（行けないはずの場所に行ける）や詰み（戻れなくなる）を見落としやすい。

core は決定論的で、画面なしで回せる（`step`、`runReplayHeadless`）。これを使えば、パックのデータから「どこに行けるか」「どこから戻れないか」を自動で調べられる。M1 時点の対象は、部屋 1 つ、キャラクター 2 人、タグ付きタイルである。M3（複数の部屋、exits、アイテム、フラグ）に拡張できる構造にしておく。

1 tick ごとに 16 通りを超える入力があり、位置と速度は 1/256 px 単位なので、素朴な全探索はできない。どこを近似し、何を保証するかを決める必要がある。

## 選択肢

| 案 | 概要 | 長所 | 短所 |
| --- | --- | --- | --- |
| 1 | 幾何だけで判定する（ジャンプの放物線を式で計算する） | 速い | 物理を二重に実装することになり、core とずれる。コヨーテタイムや可変ジャンプを式に写すたびに誤りが入る |
| 2 | 量子化した状態（位置、速度）の格子を、1 tick 単位の入力で全探索する | 入力の取りこぼしが少ない | 状態数が数百万になる。量子化した状態から先へ進めると、実際には無い経路ができる（健全でなくなる） |
| 3 | 接地状態を節点にし、入力をマクロにまとめ、core の `step` で実際に回す。同一視は「再探索の省略」だけに使う | 物理は core のまま。見つけた経路はそのままリプレイになる。状態数が小さい | マクロに無い操作でしか届かない場所を見落とす（不完全） |

## 実装の段階

本 ADR は設計の全体を決める。実装は段階に分ける（roadmap の A-1 と A-2）。

| 段階 | 範囲 |
| --- | --- |
| A-1（実装済み、2026-11-15） | キャラクター 1 人ずつの探索、マクロ（歩く、止まる、ジャンプ、踏み外しジャンプ、落下、すり抜け降下）、量子化、証拠の再生による検証、統計と上限 |
| A-2 の前半（実装済み、2026-11-16） | キャラクター 1 人の範囲での「証明」: 上昇量の上限、証明つきの到達できない理由（`enclosed`、`tooHigh`）、戻れない領域（`verified`、`provenNo`、`notFound`） |
| A-2 の残り | 切替のマクロとパーティ全体の探索、推定の理由、操作感の Property テスト、M3 への拡張設計の詳細化、上限の見直し。詳細は [solver-handoff.md](../solver-handoff.md) |

以下の「決定」のうち、パーティ、切替、理由の推定は A-2 の残りで実装する。

## 決定

案 3 を採用する。新しいパッケージ `packages/solver`（`@retro-action-engine/solver`）に置き、`core` だけに依存する。

### 原則

1. **物理は core の `step` だけを使う。** ソルバーは「どの入力を試すか」を決めるだけで、位置や速度を自分では計算しない。状態の複製は `cloneWorld`。
2. **健全性を最優先にする。** 「到達できる」と報告する足場には、必ず `ReplayFile` を付ける。報告の前に、そのリプレイを `runReplayHeadless` で最初から再生し、(a) 終端で足場の上に接地していること、(b) 終端の hash が探索時の状態と一致することを確かめる。確かめられなければ、報告せずにエラーにする（ソルバーの不具合として扱う）。
3. **完全性は保証しない。** 「見つからなかった」と「不可能だと証明できた」を、報告の上で区別する。
4. **ソルバー自身も決定論的にする。** 同じ入力なら同じ報告を返す。乱数と時計を使わず、走査順を固定する。経過時間は、呼び出し側が渡す時計で測る（渡さなければ報告しない）。
5. **固有値を書かない。** キャラクター名、タグ名、速度などは、すべて `PackRuntime` から読む。マクロの派生も操作感の値から導く。

### 足場

- 足場は、同じ高さで連続する「立てるタイル」の並び。キャラクターごとに列挙する（タグ付きタイルは、そのキャラクターの文脈で solid かどうかが変わるため）。
- タイルが「立てる」とは、そのキャラクターの文脈で `full` か `oneway` であり、当たり判定の箱をそのタイルの上面に置いて、少なくとも 1 つの x で `full` のタイルと重ならないこと。列挙には core の `solidAt` を使う。これは形の列挙であり、到達の判定には使わない。
- 「到達した」とは、探索中の状態が接地していて、その箱を支えているタイルが足場に含まれること。

### 探索（状態爆発への対策）

| 項目 | 設計 |
| --- | --- |
| 節点 | 接地している状態（着地した tick の `World`）。空中の状態は節点にしない |
| 同一視 | 節点のキーは「足元の高さ（正確な値）、x を `xQuantum` で量子化した値、vx を `vQuantum` で量子化した値」。パーティの探索（A-2）では「操作中のキャラクター、切替の cooldown が残っているか」を足す。同じキーの状態は、先に見つかった 1 つ（正確な `World`）だけを代表として残す |
| 辺 | マクロを、代表の `World` の複製に対して実際に `step` で回した結果。次に接地するまでを 1 本の辺にする |
| 探索順 | 幅優先（マクロの本数が少ない経路を証拠にする）。マクロと節点の走査順は固定 |
| 上限 | 節点数、`step` の総回数、1 マクロの tick 数に上限を置く。超えたら打ち切り、報告に `complete: false` を出す（A-2 で、残りの足場に理由 `budget` を付ける）。`step` の総回数は 1 回の `solveRoom` 全体で数える |

量子化で省くのは「似た状態からの再探索」だけである。辺は必ず代表の正確な状態からの実際のシミュレーション結果なので、健全性には影響しない。

証拠のリプレイは、探索木の親をたどって作る（親から子への辺は、親の正確な状態から実際に回した入力である）。同一視した節点への辺は、着地した状態が代表と少し違うので、証拠の経路には使わない。

### マクロ

| マクロ | 内容 | 派生のさせ方 |
| --- | --- | --- |
| 歩く | 左または右を押し続ける。x の量子が変わるか、壁で止まるか、足場を外れるまで | 2 方向 |
| 止まる | 何も押さず、vx が 0 になるまで | |
| ジャンプ | ジャンプを h tick 押す。左右の入力は「押しっぱなし（左 / なし / 右）」。着地まで | h は、`jumpCutScale` が 1 なら 1 通り。そうでなければ、`minJumpTicks` から上昇の終わりまでを等間隔に数通り（最長は必ず含む）。`airControl` が 0 でなければ「頂点で左右を切り替える」も足す |
| 踏み外しジャンプ | 歩いて足場を外れたあと、k tick 後にジャンプ | k は 0 から `coyoteTicks` までの全部。その節点からの「歩く」が足場を外れたときだけ試す |
| 落下 | 歩いて足場を外れ、そのまま落ちる | 左右の入力 3 通り |
| すり抜け降下 | 足元がすべて oneway のとき、下 + ジャンプ | 左右の入力 3 通り |
| 切替 | cooldown が切れるまで待ってから切替 | パーティの探索でだけ使う |

上昇の終わり（最長の押下時間）は、何も無い部屋で最長押しのジャンプを core で実際に回して測る。最も高く上がる押下時間は、上昇量の上限を求めるときに一緒に分かる（`measureHighestJump`）ので、それもジャンプのマクロに必ず含める（押下時間 0 を除く）。

マクロは「押しているボタンの列」だけを作る。押した瞬間と離した瞬間は、前の tick との差から求める（実機の入力と同じ形になる）。ジャンプの前にジャンプボタンが押されたままなら、先に 1 tick 離す。

### 完全性の範囲

| 観点 | 保証 | 諦める点 |
| --- | --- | --- |
| 「到達できる」 | 必ず正しい（リプレイで検証済み） | なし |
| 縦の到達高さ | 最長押しのジャンプと、最も高く上がる押下時間（`measureHighestJump`。全押しとは限らない）を必ず試す。真上が開けていれば Fx の精度で正確 | 天井をくぐるための中間の押下時間は、サンプルにある値だけ。最も高く上がるのが「ボタンを離したまま始まるジャンプ」（先行入力。押下時間 0）の操作感では、マクロは接地状態から始まるので作れず、最高点の足場を見落とす（`riseBound` による証明は正しいまま） |
| コヨーテタイム | 0〜`coyoteTicks` の全 tick を試す | |
| 横の到達距離 | 踏み切り位置は、量子ごとと足場の端で試す | 踏み切り位置の位相により、最大で「`xQuantum` と 1 tick の移動量の大きい方」の取りこぼしがありうる |
| 空中制御 | 押しっぱなしと、頂点での 1 回の切替 | それより細かい空中操作でしか届かない場所は見落とす |
| キャラクターの切替（パーティ） | 接地中の切替（cooldown が切れるまで待ってから） | 空中での切替は試さない。ジャンプ中に切り替えてしか届かない場所は見落とす |
| 予算 | 上限内なら上の範囲で網羅 | 上限を超えたら `complete: false` |
| 「到達できない」 | 下の 2 つの証明が付いたものは確実 | それ以外は「見つからなかった」 |

### 上昇量の上限

証明に使う値 `riseBound`（`measureRiseBound`）を、次の主張が成り立つように決める。

> キャラクター 1 人が、動かないタイルだけの部屋にいるとする。ある tick に足元の高さ y で接地していたなら、次に接地するまでのあいだ、どんな入力列でも、足元は y より `riseBound` を超えて上がらない。

core の `controller` と `moveBody` の実装に対する根拠:

1. **ジャンプ無しでは上がらない。** 縦の速度 vy を変えるのは、ジャンプの開始、可変ジャンプのカット、重力、fall 速度の上限、タイルとの衝突（vy を 0 にする）だけである。重力が負にならず（`gravity`、`fallGravityScale`、`apexGravityScale` がどれも 0 以上）、`maxFallSpeed` が 0 以上なら、vy が 0 以上のとき次の tick も 0 以上になる。接地中の vy は 0 なので、ジャンプするまで体は上がらない。この 4 つの条件を満たさない操作感では、上限を「なし」（無限大）にする。
2. **ジャンプは、最後に接地していた高さ以下から始まる。** ジャンプできるのは、接地中か、コヨーテタイムの間だけである。コヨーテタイムの間は 1 により落ちているだけなので、ジャンプの開始位置は、最後に接地していた高さと同じか、それより下になる。ジャンプは接地するまで 1 回しかできない（`jumpedSinceGrounded`）。
3. **ジャンプ開始後の vy は「カットされた tick」だけで決まる。** ジャンプの開始 tick に vy は `-jumpVelocity` になり、それ以前の状態によらない。その後に入力が vy に影響するのは、可変ジャンプのカット（`minJumpTicks` 以降で、ボタンが離れている最初の tick に 1 回だけ）だけである。左右の入力は vx しか変えない。
4. **何も無い空間での最大の上昇は、カットの tick をすべて試した最大値である。** カットには vy < 0 が要るので、候補は全押しの上昇が終わるまでの tick に限られる。`measureRiseBound` は、何も無い部屋で、押下時間 0（ボタンを離した状態で始まるジャンプ。先行入力で起きる）から全押しまでのすべてを core の `step` で実際に回し、最大値を返す。式で計算はしない。
5. **タイルは上昇を減らすだけである。** 天井に当たると、上昇はそこで止まり、vy が 0 になる（以降は 1 による）。壁は vx だけを変える。足場に着けば、そこが新しい基準になる。

**全押しが最大とは限らない。** 頂点付近で重力が弱まる操作感（`apexGravityScale` < 1）では、ボタンを離して減速したほうが、低重力の範囲に 1 tick 早く入り、全押しより高く上がることがある。たとえば、modern の値を `jumpCutScale` 0.95、`apexThreshold` 1px、`apexGravityScale` 0.1 に変えると、全押しの上昇は 52.2px、14 tick で離したときの上昇は 58.6px になる（core の実測）。そのため、全押しの実測値（`measureRise`。マクロの押下時間に使う）は上限としては使えない。標準の retro と modern では、両者は同じ値になる。

前提が崩れる機能（切替による位置の移動や箱の変化、動く床、ばね、敵に踏まれる、など）を足すときは、この節を見直す。

### 証明つきの「不可能」

どちらも、行ける範囲を実際より広く見積もる。そのため「不可能」という結論は確実である。シミュレーションはせず、「到達できる」の根拠には使わない。

- **開いた領域**: 開始時に箱が重なっているセルから、そのキャラクターの文脈で `full` でないセルを上下左右にたどった集合。箱は `full` のタイルに重ならず、1 軸ずつ、最大 1 タイルずつ動く（ADR-0004）ので、箱が重なるセルは常にこの集合の中にある。oneway は開いているものとして扱う。開始時に箱が `full` のタイルに重なっている場合は、この証明を使わない。
- **閉じている（`enclosed`）**: 足場のすぐ上のセルが、どの列でも開いた領域に入っていない。その足場に立つには箱がそのセルに重なる必要があるので、到達できない。
- **立てる高さ**: 支えになるタイル（`full` か oneway）があり、そのすぐ上のセルが開いた領域に入っている行の上面。「上昇量の上限」により、高さ y に立っている状態から次に立てる高さは、y より `riseBound` を超えて高くはならない。開始位置の足元の高さから、`riseBound` 以内にある立てる高さを順に登った結果を「立てる最高の高さ」とする。登るときに意味を持つのは足元より上の高さだけなので、部屋の下端（最も低い床）は数えなくてよい。途中の横の位置や壁は考えない（広く見積もる）。
- **高すぎる（`tooHigh` の証明）**: 足場の上面が、開始位置からの「立てる最高の高さ」より高い。報告には、必要な上昇量（立てる最高の高さからの差）と `riseBound` を付ける。
- 足場の一覧（`listFootholds`）ではなく、支えになるタイルを直接数える。足場の一覧は 1px 刻みで箱が収まるかを見ているので、そこから漏れた場所に立てる可能性を、証明の側では排除しないためである。

### パーティでの証明

パーティ（切替あり）の探索にも同じ証明を使う。ただし、上の根拠は「キャラクター 1 人」を前提にしている。切替で崩れる前提ごとに、成り立つ条件を決め、条件を満たさないときは**証明を出さない**。証明が無くても「到達できる」「戻れる」の報告（再生で検証）には影響しない。

| 証明 | パーティで出す条件 | 条件を満たさないとき |
| --- | --- | --- |
| 開いた領域と `enclosed` | 全メンバーの当たり判定の箱（`collider` の `w`、`h`、`ox`、`oy`）が同じ | 出さない |
| 立てる高さ、`tooHigh`、`provenNo` | 上に加えて、切替が接地中に限られ（`requireGrounded` が真）、切替で位置が変わらない（`placement` が `same`） | 出さない（`riseBound` を `null` にする） |

**開いた領域**。セルが「閉じている」とは、**どのメンバーの文脈でも** `full` であることとする（誰かが通れれば空き）。

- 移動: `moveBody` は、操作中のキャラクターの文脈で `full` のセルに新しく入らない。閉じたセルは誰の文脈でも `full` なので、移動で閉じたセルに新しく入ることはない。1 軸ずつ最大 1 タイルずつ動くので、箱が重なるセルは、開始のセルからつながった開いたセルの中にとどまる（1 人のときと同じ議論）。
- 切替: 箱が同じなら、切替の前後で箱が重なるセルは変わらない（`placement: 'same'`）。`placement: 'spawn'` では箱が開始位置へ戻る。開始位置の箱のセルは、領域をたどり始めたセルそのものである。
- 箱が違うと、切替だけで箱が閉じたセルに重なりうる（背の高いキャラクターに切り替えると、天井に頭が入る）。`moveBody` は、すでに重なっている行や列を調べないので、そこから天井を上へ抜けることがある。このとき領域の外へ出られるので、証明を出さない。
- タグが違うだけなら問題ない。たとえば、水の中で泳げるキャラクターから泳げないキャラクターへ切り替えると、箱は後者の文脈で `full` のセルに重なるが、そのセルは閉じていない（前者が通れる）。

**上昇量の上限**。パーティの `riseBound` は、メンバーごとの `measureRiseBound` の最大値とする（どれかが上限なしなら、上限なし）。根拠:

- `requireGrounded` が真なら、切替は接地している tick にしか起きない（`partyStep` は前の tick の接地の接触フラグを見る）。したがって、接地から次の接地までの空中の区間では、操作中のキャラクターは変わらない。区間の最初の tick で、新しいキャラクターの `controller` は接地として扱うので、ジャンプとコヨーテタイムの起点は「最後に接地した高さ」のままである。
- 区間の中では 1 人のときの根拠 1〜5 がそのまま成り立ち、上昇はそのキャラクターの `riseBound` 以下になる。よって、メンバーの最大値以下になる。
- 足元の高さは「箱の下端」で測る。箱が同じなら、切替で下端は動かない（箱が違うと、切替だけで足元が上がりうる。上の条件で除いている）。
- `requireGrounded` が偽だと、空中で切り替えられ、ジャンプの途中で操作感が変わる（根拠 3 が崩れる）。メンバーの操作感の「最も有利な値」を組み合わせる案は、頂点付近の重力倍率で上昇が単調に増えない（「全押しが最大とは限らない」）ので、上限になる根拠を作れない。この規則では高さの証明を出さない。
- `placement: 'spawn'` では、切替で開始位置へ移る。開始位置が足元より高いこともあるので、高さの証明を出さない。

証明と、検証済みのリプレイが食い違った場合（証明が「不可能」とした足場に検証済みのリプレイで着いた、探索で実際に起きた足場間の移動を証明が否定した）は、どちらかが誤っているので、報告せずに例外にする（`ProofError`）。

報告の型では、証明つきの理由は `certainty: 'proven'` を持つ。推定の理由（A-2 の残り）は `certainty: 'estimated'` の別の型として足し、証明つきの型には混ぜない。

### 到達できない理由の推定

証明が付かない足場には、推定の理由を付ける。推定は「ソルバーがなぜ見つけられなかったかの手がかり」であり、「不可能」の主張ではない。

- 型: 推定の理由は `certainty: 'estimated'` を持つ `EstimatedBlocker` とし、証明つきの `ProvenBlocker` とは別の型にする。報告を読む側は `certainty` で分岐する。理由の名前が同じ（`tooHigh`）でも、型が違えば主張が違う。
- 証明つきの理由がある足場には、推定を付けない。
- 推定のための解き直しも `step` の総回数の上限に数える。ただし、解き直しが上限で打ち切られても、その対象の `complete` は変えない（本来の探索の結果は変わらないため）。

上から順に判定し、最初に当てはまったものを付ける。

| 理由 | 判定 | 付ける値 |
| --- | --- | --- |
| `budget` | その対象の探索が上限で打ち切られた（`complete: false`） | なし |
| `needsTag` | 部屋のタイルクラスの `requiresAnyTag` に現れるタグのうち、対象（パーティでは全員）がまだ持っていないものを、1 つずつ全員に足した仮のキャラクターで解き直すと、その足場に立てる。タグは名前の順に試し、最初に届いたものを付ける | `tag` |
| `tooHigh`（推定） | 到達できた足場のうち、目的の足場より低いものから見て、必要な上昇量の最小値が、全押しのジャンプの実測の上昇量（`measureRise`。パーティではメンバーの最大）を超える。到達できた足場に、目的の足場と同じ高さか、それより高いものが無い | `riseNeeded`、`rise`（実測）、不足分は `riseNeeded - rise` |
| `tooFar` | 高さの足りる到達済みの足場があるのに、届いていない | なし |
| `unknown` | 上のどれでもない（到達できた足場が 1 つも無い）。いまの探索では、着地できなければ必ず打ち切り扱いになり `budget` が先に付くので、この理由は付かない。将来の変更に備えた守り | なし |

`needsTag` の解き直しでは、仮のキャラクターを `PackRuntime` にだけ足し、本来の報告には混ぜない。仮のキャラクターで届いたかどうかは、立っている足場の行と列で、目的の足場と重なるかどうかで見る（足場の一覧はタグで変わるため）。解き直しの証拠のリプレイは検証しない（推定なので、報告に経路を付けない）。

### 戻れない領域

「戻る」先は**開始の足場**（開始位置で立っている足場。開始位置が空中なら、何も押さずに最初に着地した足場）とする。到達できた足場ごとに、次の 3 つのどれかを報告する。

| 報告 | 主張 | 根拠 |
| --- | --- | --- |
| `verified` | 探索がその足場に**最初に着いた状態**から、開始の足場へ戻れる | 「行きの入力 + 帰りの入力」を 1 本のリプレイにし、最初から再生して、開始の足場の上で終わることを検証した（「到達できる」と同じゲート） |
| `provenNo` | その足場の上の**どの状態からも**、どんな入力でも戻れない | 開始の足場の上面が、その足場の高さから登れる「立てる最高の高さ」より高い（「証明つきの「不可能」」） |
| `notFound` | 最初に着いた状態からは、マクロと上限の範囲で戻る経路が見つからなかった | 探索の結果。戻れる可能性は残る |

判定の対象を決めるにあたり、次の 2 案を比べた。

| 案 | 判定の対象 | 長所 | 短所 |
| --- | --- | --- | --- |
| A | 足場に最初に着いた状態 | 足場 1 つにつき探索 1 回で済む。主張が具体的で、リプレイがそのまま再現手順になる | 同じ足場の別の状態（端に着いた場合など）は見ない。`verified` でも、別の着き方では戻れないことがありうる。`notFound` でも、別の着き方なら戻れることがありうる |
| B | 足場の上の、探索で見つけたすべての状態 | 取りこぼしが減る | 状態の数だけ探索が要る（20×10 タイルの部屋で数百〜数千回）。それでも探索で見つけた状態に限られ、「すべての状態」にはならない |

**案 A を採用する。** 理由は次のとおり。

- 「戻れない」を確実に言えるのは証明（`provenNo`）だけであり、これは案によらず「どの状態からも」成り立つ。詰みの検出で最も重要な主張は、案 A でも弱まらない。
- 案 B でも「すべての状態」は調べられないので、`verified` の意味（「戻れる状態が少なくとも 1 つある」）は本質的に変わらない。費用だけが大きく増える。
- 報告には、判定の対象が「最初に着いた状態」であることを明記する（型のコメントと本表）。

実装上の決まり:

- 「戻れる」は「到達できる」と同じ扱いにする。再生で検証できたときだけ報告する。
- 節点のグラフには、同一視した節点への辺が含まれる。そのため、グラフを逆向きにたどった結果だけで「戻れる」とは報告しない。帰りの経路は、最初に着いた状態（正確な `World`）から探索をやり直して求める。開始の足場に着地した時点で打ち切る。
- 先に `provenNo` を調べ、証明できた足場では探索をしない。
- 帰りの探索も `step` の総回数の上限に数える。上限で打ち切られた場合は `notFound` とし、`complete: false` にする。

### 出力

`solveRoom(runtime, start, options)` が `SolveReport`（JSON にできる）を返す。

| 出力 | 内容 |
| --- | --- |
| 対象ごとの結果 | キャラクター 1 人ずつ（`StartState.party` を 1 人にして解く）と、パーティ全体（切替あり、A-2） |
| 足場のグラフ | 節点は足場、辺は「どのマクロの種類で移れたか」 |
| 証拠 | 到達できた足場ごとに、検証済みの `ReplayFile` と tick 数 |
| 到達できない足場 | 一覧と理由（証明つきか推定かを型で区別） |
| 戻れるか | 到達できた足場ごとに `verified`（リプレイつき）、`provenNo`、`notFound` |
| 上昇量の上限 | 対象ごとの `riseBound`（上限なしの場合は `null`） |
| 統計 | 節点数、辺の数、試したマクロ数、`step` の総回数、経過時間、上限に達したか |

### ソルバーの定数

エンジンではなく解析の定数であり、すべてオプションで変えられる。

| 定数 | 既定 | 導き方 |
| --- | --- | --- |
| `xQuantum` | タイルの 1/8（最小 1px） | `runtime.tileSize` から |
| `vQuantum` | 操作中のキャラクターの `runSpeed` の 1/2（最小 1/256 px） | 操作感から |
| `jumpHoldSamples` | 4 | 押下時間のサンプル数 |
| `maxMacroTicks` | 600 | 1 マクロの上限 |
| `maxNodes` | 20,000 | 節点数の上限 |
| `maxSteps` | 50,000,000 | `step` の総回数の上限（1 回の `solveRoom` 全体）。A-2 の実測で 20,000,000 から変更 |

A-1 の実測（この環境の Node 22、1 スレッド。おおよそ毎秒 130 万 step）:

### M3 への拡張（設計のみ。A-3 で実装する）

A-2 までの「部屋 1 つの中の移動」を下の層とし、その上に「鍵と扉のグラフ」を置く。下の層の原則（物理は `step` だけ、「できる」は再生で検証、「不可能」は広く見積もった外側だけ）は、上の層でもそのまま守る。

#### 状態の分け方

| 種類 | 例 | 扱い |
| --- | --- | --- |
| 単調に増える鍵 | 装備アイテムの `grants`、`switch` ギミックが立てるフラグ、`breakable` を壊した記録 | 不動点の計算に使う（下記） |
| 単調でない鍵 | `consumesItem` で消える鍵、フラグによる `revokes`（ADR-0007）、イベントの `setPartyMember` による離脱 | 不動点に入れない。「できる」は検証済みの経路だけで言い、「不可能」は消えないものとみなして広く見積もる |
| 時間で変わるもの | 敵、`spawner`、動く床（M5） | 探索の `World` にはそのまま含める（`step` が動かす）。同一視のキーには入れない。高さの証明は使わない（下記） |

#### 上の層のグラフ（型の案）

```ts
/** 部屋 × 足場のまとまり。足場の id は A-2 の run の id。 */
interface PlaceNode { readonly roomId: string; readonly runId: string }

type KeyId = `tag:${string}` | `flag:${string}` | `item:${string}`;

type WorldEdge =
  /** 部屋の中の移動。A-2 の solveRoom の辺 */
  | { kind: 'move'; from: PlaceNode; to: PlaceNode }
  /** exits（edge / door / warp）。requires は exit の requiresAnyTag と requiresFlag */
  | { kind: 'exit'; from: PlaceNode; to: PlaceNode; requires: readonly KeyId[] }
  /** 鍵が手に入る場所（pickup、switch、breakable）。at の足場から箱が届く */
  | { kind: 'key'; at: PlaceNode; gives: KeyId; consumable: boolean }
  /** gate。opensFlag を立てる。consumesItem があれば鍵を 1 つ使う */
  | { kind: 'gate'; at: PlaceNode; requires: readonly KeyId[]; consumes?: KeyId; gives: KeyId };

interface WorldReport {
  readonly places: ReadonlyArray<PlaceNode & { status: 'reached' | 'unreached'; witness?: Witness }>;
  /** 不動点の各段で、新しく手に入った鍵 */
  readonly rounds: ReadonlyArray<{ readonly keys: readonly KeyId[] }>;
}
```

#### 不動点の計算

1. 鍵の集合 K を空（初期の所持品とフラグだけ）で始める。
2. 開始の部屋から、K で通れる exit をたどりながら、各部屋を A-2 の方法で解く。部屋の探索は、その部屋に入った**正確な `World`**（検証済みの経路の終端）から始める。`createWorld` からは始めない（フラグ、所持品、HP が経路で変わるため）。
3. 到達できた場所から届く「単調に増える鍵」を K に足す。
4. K が増えたら 2 に戻る。増えなければ終わる。

止まることの根拠: 単調に増える鍵はパックのデータで有限個（タグ、フラグ、アイテムの数）であり、各段で少なくとも 1 つ増えるか、そこで終わる。段の数は鍵の数以下になる。

#### 「できる」の証拠

- 部屋をまたぐ証拠は、ゲームの開始からの 1 本の `ReplayFile` とする。部屋ごとの区間の入力をつなげ、`runReplayHeadless` で最初から再生して検証する（部屋の遷移も core が `step` の中で行う）。
- 鍵が「手に入る」の判定も同じゲートを通す。終端で、所持品やフラグが実際に変わっていることを `World` で確かめる。箱がオブジェクトの矩形に重なるかを、ソルバーが自分で計算して判定しない。
- 探索の目標を「足場に着く」から「状態の条件を満たす」に広げる（A-2 の目標つきの探索の `goal` を、足場の一覧ではなく `World` を受け取る関数にする）。

#### 「不可能」の証明

- 開いた領域を部屋をまたいで広げる。exit は、要件（`requiresAnyTag`、`requiresFlag`）を無視してすべて通れるものとし、タグはパックのどこかで手に入るものを全部持っているものとする。鍵は消えないものとする。どれも行ける範囲を広く見積もる側なので、その外側は確実に届かない。
- 高さの証明は、部屋ごとに A-2 の条件で使う。ただし、体を上へ動かしうるもの（動く床、ばね、上向きのノックバックを持つ敵）が部屋にあれば、その部屋では使わない。判定はパックのデータ（ギミックの種別、敵の振る舞い）から行う。
- 「戻れない」の戻り先は、開始の部屋の開始の足場とする。`provenNo` は、上の広い見積もりのグラフで、戻る経路が無いことで示す。

#### 単調でないものの扱い（案）

- 消える鍵（`consumesItem`）: 使う順序で詰むことがある。「できる」は検証済みの経路の個数どおりなので正しい。詰みの検出は別の検査とし、「鍵の種類ごとに、手に入る数の合計 < 消費するゲートの数」の部屋の組を警告として出す（証明ではなく推定）。順序を全部調べる検査は、ゲートの数が少ないときに限って A-3 で検討する。
- `revokes`: フラグでタグが消える。そのフラグを立てうる経路の後ろでは、タグを持たないものとして解く（広く見積もる側では、消えないものとする）。
- 敵: 同一視のキーに敵の状態を入れないので、敵の位置の違う状態が同じ節点になる。これは「再探索の省略」であり、健全性には影響しない（証拠は再生で検証する）。完全性は下がる。
- 死亡と復帰（`respawnAtSavePoint`）: セーブポイントへのワープとして辺にする。探索の打ち切りにはしない。

#### パック仕様との食い違い・未定の点（A-3 の前に決める）

- `pickup`、`switch`、`gate` が「触れた」とみなす条件（箱とオブジェクトの矩形の重なりか、操作ボタンか）が `pack-spec.md` に無い。鍵の取得をゲートで確かめる方法がこれで決まる。
- `pickup.onceFlag` が無い場合、部屋に入り直すたびに鍵が復活するのか。復活するなら、消える鍵の数え方が変わる（無限に手に入る）。
- `breakable` を壊した状態が保存されるか（フラグで残るか）が書かれていない。残らないなら「単調に増える鍵」ではない。
- `items.json` の `grants` は「所持中に付与」で、`rules.inventory.scope` で付く相手が決まる（ADR-0007）。消耗品（`consumable`）に `grants` があると、使ったときにタグが消える。単調に増える鍵として扱えるのは `equipment` と `upgrade` だけにするのが安全。
- `gating.subject: 'active'` の規則では、ゲートは操作中のキャラクターのタグで評価される。パーティの探索では、ゲートの前で誰が操作中かを状態に含める必要がある（A-2 のキーには入っている）。

## 結果

- 得られるもの: 抜け道と詰みの自動検出。見つけた経路はそのままリプレイとして再生でき、Feel scenario や Golden の入力にも使える。操作感の値を変えたときに、行ける範囲がどう変わるかを機械的に確かめられる。
- 失うもの: 完全性。マクロに無い操作でしか届かない場所は「見つからなかった」になる。解析の実行時間（部屋の広さと操作感の自由度に比例する）。
- 依存方向: `solver → core` のみ。エンジンの実行時（`apps/player`）には含めない。`architecture.md` 3 章と `.dependency-cruiser.cjs` に反映する。
- テストの fixture は core の `test-support.ts` を `@retro-action-engine/core/testing` として再利用する。テスト以外からの import は dependency-cruiser で禁止する。
- フォローアップ: A-2（パーティ、戻れない領域、理由の推定）、A-3（M3-3 の後。鍵と扉のグラフ）、A-4（M4。`pack-cli validate` への組み込みと、サンプルパックの CI 検査）。

## 要確認

- 既定の上限（`maxNodes`、`maxSteps`）は、サンプルパックの部屋（M1-5 の後）と、パーティの探索（A-2）で実測して見直す。
- 敵や移動床など、時間で変わる障害物の扱い（M3-4、M5-3）。接地状態のキーに「周期の位相」を足す案があるが、A-3 で判断する。
- 「M3 への拡張」の「パック仕様との食い違い・未定の点」。A-3 の ADR を書く前に、`pack-spec.md` 側で決める。
